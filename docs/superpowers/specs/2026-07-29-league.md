# League — Design Spec

**Date:** 2026-07-29
**Status:** Approved (MVP scope)

## Background

The site currently serves Tangerine Toucans FC's own club (parents registering their own kids to play for the club). This adds a new, separate concept: a **League** that other clubs can register their teams into, with fixtures, a standings table, and (later) a top-scorer leaderboard. This is entirely distinct from individual player registration — a club registering a team is not the same as a parent registering a child.

## Scope

**This build (MVP):**
- League tab with Fixtures, Table, and Register Team sub-sections
- Club/team/player registration (admin-approved, no club login)
- Division management (age groups), each with its own fixtures/table
- Auto-generated home-and-away round-robin schedule per division, with per-fixture manual editing
- Admin score entry and auto-computed standings table

**Explicitly out of scope for this build (Phase 2 fast-follow):**
- Top Scorer leaderboard (tab exists but shown as "coming soon")
- Club manager logins / self-service roster management — admin handles all registration approval and roster changes centrally for now

## Navigation & page structure

A new top-level **"League"** nav item links to `/league`, which has an internal tab strip:

**Fixtures | Table | Top Scorer (disabled/"coming soon") | Register Team**

All four live under one URL with client-side tab switching — no separate page loads. This is fully independent of the existing `/register` (individual Tangerine Toucans player registration); no shared components or data between the two.

## Data model

New tables (Postgres, matching the existing schema conventions — enums for status fields, `created_at`/`updated_at` timestamps, RLS via service-role server actions as with the rest of the site):

- **`league_clubs`** — `name`, `contact_name`, `contact_email`, `contact_phone`, `badge_url` (Cloudinary, nullable), `status` (`pending` / `approved` / `rejected`)
- **`league_divisions`** — `name` (e.g. "U12"), `season_start_date`, `season_end_date`
- **`league_teams`** — `club_id` (FK → `league_clubs`), `division_id` (FK → `league_divisions`), `name`, `status` (`pending` / `approved` / `rejected`)
- **`league_players`** — `team_id` (FK → `league_teams`), `name`, `date_of_birth`, `squad_number`, `status` (`pending` / `approved` / `rejected`)
- **`league_fixtures`** — `division_id` (FK), `home_team_id` (FK → `league_teams`), `away_team_id` (FK → `league_teams`), `match_date`, `home_score` (nullable until played), `away_score` (nullable until played)

A club can have multiple teams (e.g. one per division/age group). A team belongs to exactly one division.

**Squad number uniqueness:** enforced with a partial unique index on `(team_id, squad_number) WHERE status = 'approved'`. Since submissions are anonymous (no visibility into already-taken numbers), a collision is only caught at *approval* time, not submission time: if approving a pending player would violate the constraint, the approval action fails with a message telling admin to ask the club for a different number before re-submitting. This is an accepted manual step, not a built conflict-resolution UI.

**Division "open" status:** a division accepts new team registrations up until admin clicks "Generate Schedule" for it — there's no separate open/closed flag, this is simply derived from whether the division has any fixtures yet. Once a schedule exists, new teams cannot join that division (their registration would need a new division, or manual fixture addition — see below). Player registration/additions to an *already-approved* team remain open all season regardless of schedule generation.

## Registration flow (public, no login required)

One "Register Team" form under the League tab's Register Team tab, handling two cases via a mode toggle at the top:

1. **Register a new team** — club details (name, contact name, email, phone, badge upload) + team name + division selection (from currently open divisions — see "Division open status" below) + initial roster (one or more players: name, DOB, squad number). There is no club lookup/dedup at submission time — every submission creates a fresh `league_clubs` row, even if the same club is registering a second team for a different age group. If this produces duplicate club records, admin merges/reconciles them manually as a one-off cleanup action; this is an accepted MVP limitation, not a built feature.
2. **Add a player to an existing team** — select club, then team (from a dropdown of approved teams), then submit one new player's details (name, DOB, squad number)

Both submission types land in the same admin approval queue, following the same pending/approve/reject pattern already used for Gallery photo submissions and Get Involved form submissions. Nothing is publicly visible (team doesn't appear in its division, player isn't on a roster) until approved.

## Fixtures & schedule generation

1. Admin creates a **Division** (name + season start/end date) via `/admin`.
2. Clubs register teams into that division (subject to approval).
3. Once team registrations are approved, admin clicks **"Generate Schedule"** for that division. This creates a full home-and-away round-robin: every approved team plays every other approved team twice (once home, once away), with match dates spread evenly across the division's start/end date range. If the division has an odd number of approved teams, the standard round-robin "bye" technique is used internally (a phantom team that generates no real fixtures) — each real team simply has one fewer match in whichever round they'd have faced the bye.
4. Every generated fixture remains **individually editable** afterward — admin can change a fixture's date/time or swap which teams are assigned, to handle real-world constraints (e.g., "Team X can only play Sundays").
5. Admin can also **manually add a single fixture** to a division at any time (e.g. correcting an omission, or giving a team that registered after schedule generation a game) — this doesn't regenerate anything, it just inserts one more fixture row.
6. As matches are played, admin enters the final score (home/away) on each fixture.

Regenerating a *full* schedule for a division that already has fixtures is not supported in this build — if teams change significantly, admin edits/adds fixtures manually. (Out of scope: automatic re-scheduling.)

**Team withdrawal mid-season** (a team dropping out after fixtures exist) is not handled by any specific feature in this build — deferred until it's actually needed. If it happens, admin will manually edit or delete the affected fixtures as a one-off action.

## League Table

Computed on read (not stored) from a division's played fixtures (those with non-null scores):
- 3 points for a win, 1 for a draw, 0 for a loss
- Ranked by: points → goal difference → goals scored (all descending)
- Displayed as a compact table: rank, badge, team name, P/W/D/L/GD/Pts

Each division has its own independent table.

## Admin workflow (additions to `/admin`)

- **Pending queue** — approve/reject club registrations, team registrations, and individual player additions (mirrors the existing Get Involved / Gallery submission queues)
- **Division management** — create/edit divisions (name, season date range), trigger schedule generation
- **Fixture management** — list fixtures per division, edit date/teams, add a single fixture manually, enter scores

## Out of scope (this build)

- Top Scorer leaderboard (goal-scorer tracking per fixture) — Phase 2
- Club manager self-service logins — Phase 2
- Automatic fixture re-generation after a schedule already exists
- Cross-division fixtures/table (e.g. inter-division cup matches)
- Payment/fees for league registration (not mentioned as a requirement; assumed free to register for now)
- Club dedup/lookup at registration time — duplicate club records are an accepted possibility, resolved manually by admin if they occur
- Team withdrawal handling — no dedicated feature; admin manually adjusts fixtures if a team drops out mid-season
